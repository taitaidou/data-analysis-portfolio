# 游戏 APP 用户活跃与留存分析

**工具：** BigQuery SQL、Tableau  
**项目时间：** 2025.08–2025.10

## 分析目标

分析游戏用户活跃、留存和关键行为转化，识别新用户进入核心玩法及关卡后虚拟货币消费的优化机会。

## 数据与方法

使用 Google Firebase 公开游戏事件表 `firebase-public-project.analytics_153293282.events_*`。已提供[SQL 查询](sql/README.md)和[八份汇总结果及口径说明](data/README.md)。当前汇总数据日期范围为 2018-06-12 至 2018-10-03，与项目开展时间不同。

- 清洗与聚合事件数据，计算 DAU、WAU、D1/D7 留存等指标。
- 统计首次启动、开始关卡、完成关卡和虚拟货币消费等事件的覆盖人数；当前 SQL 尚未限制事件顺序，严格时序漏斗待完善。
- 按 Cohort 和活跃频次分析留存与用户行为差异。

## 结果与交付

以下结果根据仓库内已上传 CSV 复算或摘录，未重新连接 BigQuery 执行查询，也不代表已经实现业务增长。

### 1. 数据覆盖与用户活跃

- 当前导出数据覆盖 **2018-06-12 至 2018-10-03，共 114 天**；[每日活跃结果](data/processed/daily_activity.csv)的事件数合计为 **5,700,000 条**。
- [Cohort 结果](data/processed/cohort_retention.csv)的首次出现用户数合计为 **15,175 人**，与[活跃分层表](data/processed/activity_segments.csv)各互斥分组人数之和一致。该人数按现有导出表口径汇总，并非通过每日 DAU 相加得到。
- 已在看板中展示 DAU、滚动七日 WAU 及其时间变化。WAU 指当日及前六日产生过事件的去重用户数。

> 当前每日事件数均为 50,000，数据是否存在固定条数抽样或截断尚未确认。因此，上述规模只描述当前导出样本，不推断为游戏真实全量业务规模。

### 2. Cohort 留存

为避免将未观察满七天的用户计入 D7 分母，本节对 D1、D7 统一使用 **2018-06-12 至 2018-09-26** 首次出现的 **107 个 Cohort、14,494 名用户**：

| 指标 | 对应日期回访人数 | 纳入用户数 | 加权整体留存率 |
| --- | ---: | ---: | ---: |
| D1 留存 | 2,314 | 14,494 | **15.97%** |
| D7 留存 | 1,072 | 14,494 | **7.40%** |

计算方式为“对应留存人数合计 ÷ 纳入用户数合计”，不是各日留存率的简单平均。D1 与 D7 使用相同 Cohort 范围；如果为 D1 单独纳入观察满一天的 Cohort，需要另行计算，不能与本表混用。

“首次出现”是用户在当前数据范围内的首次记录，不等同于已验证的真实注册日或首次安装日。原始 CSV 和 SQL 保留全部 Cohort，本节通过筛选完整观察窗口复算；不表示原始 SQL 已修正，也未核验在线工作簿是否使用完全相同的筛选。

### 3. 用户活跃分层

[活跃频次汇总表](data/processed/activity_segments.csv)记录了以下用户结构：

| 用户分组 | 用户数 | 占分层表总人数比例 | 平均活跃天数 |
| --- | ---: | ---: | ---: |
| 一次性用户 | 7,856 | 51.77% | 1.00 |
| 低活跃用户 | 4,753 | 31.32% | 2.60 |
| 中活跃用户 | 1,830 | 12.06% | 7.64 |
| 高活跃用户 | 736 | 4.85% | 33.73 |
| 合计 | 15,175 | 100.00% | — |

各比例由分组人数除以 15,175 计算。该结果展示当前分层表中的群体结构；分层阈值和生成 SQL 尚待补充，因此暂不推断具体流失原因或运营效果。


### 4. 版本表现

[版本汇总表](data/processed/version_performance.csv)中，用户覆盖数前三的版本为：

| 版本 | 去重用户数 | 事件数 | 人均事件数 |
| --- | ---: | ---: | ---: |
| 2.62 | 6,591 | 2,753,998 | 417.84 |
| 2.6.31 | 3,911 | 1,461,036 | 373.57 |
| 2.6.30 | 3,568 | 688,468 | 192.96 |

人均事件数为该版本事件数除以该版本去重用户数。同一用户可能出现在多个版本，版本人数不能直接相加作为总用户数；不同版本的上线时间、用户构成和观察时长未对齐，因此该表用于描述差异，不能据此判定版本质量或发布的因果效果。

### 5. 分析建议与验证路径

- **新用户引导：**将进入核心玩法作为后续分析方向；先构建严格时序漏斗，确认主要流失环节，再提出具体引导改动。
- **分层运营：**围绕一次性用户与高活跃用户分别设计引导、召回和维护方案；补齐分层阈值，并结合留存和回访数据评估。
- **版本差异排查：**在相同观察窗口内按国家、设备及用户资历比较版本，区分埋点变化与用户行为变化，再判断是否需要产品调整。

上述内容均为待验证的建议
